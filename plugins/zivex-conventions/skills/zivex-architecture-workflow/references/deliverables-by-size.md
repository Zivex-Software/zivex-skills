# Deliverables by size

Scale the paperwork to the risk. Bigger is not better; **enforced** is better.

| Size   | Typical work                                                                                                                                                       | Architecture deliverables                                                                                                                                                                                                           | Gate                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| **XS** | A local change, copy, a small bug                                                                                                                                  | None. A regression test for bugs                                                                                                                                                                                                    | none                    |
| **S**  | A bounded feature inside one module                                                                                                                                | A `DECISIONS.md` entry if a choice was made                                                                                                                                                                                         | none                    |
| **M**  | A multi-file feature, a new endpoint group, a new screen set                                                                                                       | A short design note in the module doc (flows, data, capabilities, events, tests). An ADR if it touches a boundary, security or a contract                                                                                           | none (a report)         |
| **L**  | A new module in an existing system; a new small system (a website, a single integration, a small internal app)                                                     | A **lite masterplan** (parts A to C, roughly 300 to 900 lines), the baseline ADRs that differ from the house default plus tenancy, authorization and data ADRs, data classification, a one-page threat model, a lite control matrix | owner approves the plan |
| **XL** | A new product or platform, a multi-client system, anything critical (auth, payments, health data), a cross-product integration, an architecture or security change | A **full masterplan** (all sections), the full baseline ADR set, a threat model per trust boundary, the full compliance pack, a phased roadmap of vertical slices, an agent orchestration plan, an independent review               | owner approves the plan |

Upgrade one size when the work touches: authentication or sessions, money, special-category personal data, cross-tenant boundaries, a public contract (API, event, SDK), or a production data migration.

## Per system type: what is always included

| Type                     | Always included                                                                                                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Client web app or portal | Identity integration (backend-for-frontend), tenancy design, capability table, audit, customer-safe projections if customers see data                                   |
| Own SaaS                 | Everything above plus entitlements and plans, metering, environments and sandboxes, a public API and SDK plan, status and SLA, data export                              |
| Integration              | The integration boundary (or an interim adapter ADR), idempotency and replay, credential custody, failure, park and retry, a mapping specification with golden fixtures |
| Website or shop          | Content models, pages, navigation, an SEO and redirect map, forms, i18n, an accessibility statement, hosting, a performance budget                                      |
| Mobile or desktop        | A native-core ADR, the edge list, offline and sync design, the auth flow (system browser and PKCE), the store and signing pipeline, a mobile verification level         |
| Rust or Go service       | An extraction ADR (why not the monolith), API and event contracts, SLOs, container hardening, an operational runbook                                                    |
